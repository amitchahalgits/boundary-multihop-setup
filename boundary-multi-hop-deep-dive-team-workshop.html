Part 1: In-Depth Parameter Reference

1. Controller Configuration (controller.hcl)

Block / Parameter Configured Value Technical Function
database.url postgresql://...:5432/boundary Primary state store connection. Holds scopes, targets, host catalogs, and audit session events.
public_cluster_addr 127.0.0.1:9201 The network address advertised to workers for gRPC control plane interconnect and heartbeats.
listener[api] 0.0.0.0:9200 Serves the REST/gRPC API and the Admin Web Console for users and administrators.
listener[cluster] 0.0.0.0:9201 Private gRPC listener used exclusively for worker registration and node enrollment.
kms[worker-auth] AEAD AES-GCM Key Shared symmetric key used for Worker-Led Authentication. Allows workers to self-enroll without manual tokens.

2. Ingress & Egress Workers (worker-ingress.hcl & worker-egress.hcl)

Worker Component Key Parameter Configuration Value How It Works
Ingress Worker initial_upstreams ["127.0.0.1:9201"] Dials the Controller Cluster listener to register into the edge layer.
Ingress Worker tags type = ["ingress"] Matched by target's -ingress-worker-filter expression.
Egress Worker initial_upstreams ["127.0.0.1:9202"] Critical Multi-Hop Binding: Dials Ingress Worker proxy port, registering itself as downstream in the routing DAG.
Egress Worker tags type = ["egress"] Matched by target's -egress-worker-filter expression.

3. CLI Target Provisioning Parameters

TARGET_ID=$(boundary targets create ssh \
  -scope-id "$PROJECT_ID" \
  -name "multihop-ssh-target" \
  -default-port 2222 \
  -session-max-seconds 28800 \
  -ingress-worker-filter '"ingress" in "/tags/type"' \
  -egress-worker-filter '"egress" in "/tags/type"' \
  -format=json | jq -r '.item.id')
  • -default-port 2222: Target destination port on the container.
  • -session-max-seconds 28800: Hard ceiling on session lifetime (8 hours).
  • -ingress-worker-filter: Directs client entry point to the Ingress edge worker.
  • -egress-worker-filter: Directs destination hop to the internal VPC egress worker.

Part 2: Team Dry-Run Troubleshooting Workshop

Run these 3 failure scenarios with your engineering team to test diagnostic skills across each layer of the architecture.

Scenario 1: Ingress Layer Failure (Filter Tag Mismatch)
Error: server.(Repository).SelectSessionWorkers: error #133

1. Inject the Bug: Update target ingress filter to look for a non-existent worker tag:

boundary targets update ssh -id "$TARGET_ID" -ingress-worker-filter '"public-dmz" in "/tags/env"'

2. Symptom When User Connects:

boundary connect ssh -target-id "$TARGET_ID"
# Error: No workers are available to handle this session.: error #133

3. Diagnostic Steps for Team:

  1. Check registered worker tags: boundary workers list -scope-id global and boundary workers read -id <id>.
  2. Inspect target filter rules: boundary targets read -id "$TARGET_ID".
  3. Identify that worker tag env=["dmz"] does not match filter public-dmz.

4. Resolution:

boundary targets update ssh -id "$TARGET_ID" -ingress-worker-filter '"dmz" in "/tags/env"'
Scenario 2: Egress Layer Failure (Broken Multi-Hop DAG Mesh)
Error: No ingress workers with valid next-hop paths could be found

1. Inject the Bug: In worker-egress.hcl, change initial_upstreams to point to Controller :9201 instead of Ingress Worker :9202, then restart egress worker:

# Set initial_upstreams = ["127.0.0.1:9201"] in worker-egress.hcl
pkill -f "worker-egress.hcl" || true
boundary server -config worker-egress.hcl > worker-egress.log 2>&1 &

2. Symptom When User Connects:

boundary connect ssh -target-id "$TARGET_ID"
# Error: server.filterWorkersEnt: No ingress workers with valid next-hop paths could be found for this multi-hop session.

3. Diagnostic Steps for Team:

  1. Notice both workers are active, but Controller cannot find a multi-hop routing path.
  2. Examine worker-egress.hcl upstream setting: Egress worker is dialing the Controller directly instead of the Ingress worker proxy listener.

4. Resolution:

# Reset initial_upstreams = ["127.0.0.1:9202"] in worker-egress.hcl
pkill -f "worker-egress.hcl" || true
boundary server -config worker-egress.hcl > worker-egress.log 2>&1 &
Scenario 3: Target Layer Failure (Container Port Mismatch)
Error: Connection closed by 127.0.0.1 port <ephemeral>

1. Inject the Bug: Re-run the OpenSSH container with wrong internal port mapping (-p 2222:22 instead of -p 2222:2222):

podman rm -f ssh-target-box
podman run -d --name ssh-target-box -p 2222:22 -e USER_NAME=testuser -e USER_PASSWORD=testpassword lscr.io/linuxserver/openssh-server:latest

2. Symptom When User Connects:

boundary connect ssh -target-id "$TARGET_ID"
# Connection closed by 127.0.0.1 port 46139

3. Diagnostic Steps for Team:

  1. Check controller logs: Authorization and worker mesh routing succeeded ([w_ingress w_egress]).
  2. Check target container logs: podman logs ssh-target-box shows sshd is listening on port 2222 inside container.
  3. Identify that Podman mapped host port 2222 to container port 22 where nothing is listening.

4. Resolution:

podman rm -f ssh-target-box
podman run -d --name ssh-target-box --restart always -p 2222:2222 -e USER_NAME=testuser -e USER_PASSWORD=testpassword -e PASSWORD_ACCESS=true lscr.io/linuxserver/openssh-server:latest
